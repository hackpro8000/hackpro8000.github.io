How I build

The habits that keep a growing game changeable.

  1. The server decides, clients display. Anything players could exploit is validated and owned on the server.
  2. State changes go through named actions. That makes every change easy to hook, replicate, test and undo.
  3. Validate at the boundary and fail loudly. Bad data produces an error that names the problem, not a mystery three systems later.
  4. Layers only depend downward. Game logic composes reusable systems, and systems don't reach back up into the game.
  5. Budget the work. Heavy jobs yield on a time slice and can be cancelled, so players never see a freeze.
  6. Type what I can. Strict Luau on the larger projects catches mistakes before a playtest does.

No. I can work entirely inside Roblox Studio and hand back ModuleScripts you can read and edit there. If your project already uses Rojo, Wally or Aftman, I'll work inside that setup and follow your conventions.

Can you work with code I already have?

Yes. I read what's there first, follow its structure and naming, and keep changes focused so you can see exactly what I touched.

How do you stop players from exploiting my game?

The server owns anything that matters. Clients send requests, the server validates them and decides the outcome, and clients only display the result.

How do you keep a game from lagging or freezing?

Heavy work, like loading a big map, is spread across frames on a time budget and can be cancelled. Searches such as pathfinding are capped so one expensive request can't stall the server.

Will I be able to understand and edit what you build?

That's the aim. I keep scripts small and clearly named, comment the parts that aren't obvious, and explain where to change things.

Coding conventions
Structure
Three layers: Core, Systems, Game. Dependencies only point downward. Core knows almost nothing about the game, Systems are reusable capabilities, and Game composes them into something specific.
Composition
Composition over inheritance. I only generalise something once it has real, recurring reuse, and I don't build abstractions for hypothetical needs. A mechanism should survive a complete change of theme.
Naming
Full, descriptive names (destinationAlpha, not da). PascalCase for methods and named error reasons, camelCase for locals, UPPER_SNAKE for constants, and a leading underscore for private fields. Folders are CapitalizedCamelCase. I only use words like Service, Manager or Handler when they're accurate.
Types
New modules start with --!strict. I annotate where it adds safety or clarity, and I avoid type gymnastics that make code harder to read.
Style
Obvious over clever. Early returns over deep nesting. A short header comment says what a file is for, and other comments explain intent, constraints and edge cases rather than narrating the code.
Ownership
Every object has a visible creator, owner and destroyer. Dependencies are passed in explicitly, with no hidden registries, service locators or global containers. Anything that owns connections, tasks or instances cleans them up on Destroy.
Errors
Listener errors are never swallowed silently. Bad input is rejected with a named reason. A failed startup stops loudly, and one failing background task doesn't take down unrelated ones.
Startup
Load everything first, then start anything. Startup is deterministic and readable, so you can see what ran and in what order.
Dependencies
No external framework unless it solves a concrete problem that a small local solution can't. The framework serves the game, not the other way round.
Project layout
Source on the filesystem rather than only inside Studio, with a minimal folder tree and predictable paths. Important logic lives in version control.
